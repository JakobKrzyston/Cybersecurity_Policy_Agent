  Slice 4: Reasoner — TDD Plan

  Three components to build; here are the behaviors I'd test (public interface
  only):

  build_system_prompt() — pure function, no faking needed

  1. Output contains the agent role/persona string
  2. Output contains policy chunks formatted with their section IDs
  3. Output contains the trust tier and risk classification
  4. Output contains the tool registry (all five tool names)
  5. No policy content leaks when we separately format the user message (user
  message = request text only)

  instrumented_llm_call() — injectable Anthropic client for testing

  6. Appends an LLM span to the tracer with latency_ms, input_tokens,
  output_tokens, cached_tokens, cost, retries
  7. Cost computed as input_tokens * input_price + output_tokens * output_price
  from model_prices.json
  8. Returns raw response content

  reason() — injected LLM, end-to-end behavior

  9. Valid JSON from LLM → returns ReasonerDecision (Pydantic-validated)
  10. Invalid JSON from LLM → returns ReasonerDecision with action="escalate"
  and safe user message
  11. Pydantic-valid JSON but wrong shape → same escalate path
  12. Model ID is read from config, not hardcoded (verified via the span logged
  in the tracer)

  Interface design question: reason() needs a way to inject a fake LLM for tests
   without making real API calls. Options:
  - Accept an optional llm_call_fn parameter (callable) — simple, no class
  needed
  - Separate build_system_prompt() so tests can verify it independently

  I'd go with build_system_prompt(session, policy_chunks, trust_tier, risk) -> 
  str as a standalone exportable function (easy to test in isolation), and
  reason(session, policy_chunks, tracer, llm_call_fn=None) where llm_call_fn
  defaults to the real instrumented_llm_call.

  ReasonerDecision; any parse or schema error falls back to a safe escalate

  hardcoded; injectable llm_call_fn for testing
