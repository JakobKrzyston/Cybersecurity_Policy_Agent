⏺ Question 3: Who determines Risk Classification, and when?

  You now have two separate dimensions the Trust Gate needs to produce: trust 
  tier (from live auth/device signals) and risk classification (Red/Grey/Blue,
  behavioral/intent-based).

  The trust tier is straightforward — it reads deterministic signals from the
  session at request time.

  Risk classification is harder. There are two plausible sources:

  - A. External register only — IT Security maintains a blocklist/watchlist in a
   security register. The Trust Gate looks up the requester's identity and reads
   their current classification. If not in the register, default is blue.
  (Simple and deterministic, but blind to in-session behavioral signals.)
  - B. In-session behavioral signals only — The Trust Gate analyzes the current
  request for urgency framing, claimed authority without basis, patterns
  consistent with 7.3, etc. No external register. (Catches novel attackers, but 
  requires the Trust Gate to do lightweight NLP — which starts to blur 
  "deterministic code" vs "LLM.")
  - C. Both, layered — External register check first (hard override), then
  in-session behavioral heuristics on top. A register red can never be
  overridden by good behavior in-session; a register blue can still be elevated
  to grey or red by the current request. (Recommended — this matches how section
   13.1 and 5.3.c work: IT Security flags sessions externally, but the agent 
  also escalates based on cumulative in-session signals.)

  Which model do you want, and — critically — if behavioral heuristics are
  involved, do they run as deterministic rules or as a small LLM call at the
  gate?

⏺ Question 4: How does the Reasoner output its decisions?

  Your README says the Reasoner "outputs intent, not execution" and gives this
  structured format:

  {
    "action": "allow|deny|escalate|clarify",
    "tool_calls": [...],
    "reasoning": "...",
    "cited_sections": [...],
    "user_message_draft": "..."
  }

  The Anthropic API already has a built-in mechanism for this: the model returns
   tool_use content blocks, and your code decides whether to execute them.
  That's "intent not execution" by the nature of the API.

  So there are two distinct implementations here:

  - A. Standard Claude tool_use — The Reasoner uses the API's native tool_use
  mechanism. The Tool Executor receives tool_use blocks and re-validates before
  calling each mock tool. The action, reasoning, cited_sections, and
  user_message_draft fields come from a separate structured output or a text
  block alongside the tool calls. (Recommended — you get the API's built-in tool
   parsing, retries, and schema validation for free. The separation you want is 
  already inherent.)
  - B. Custom JSON output — The Reasoner is instructed to output a raw JSON blob
   (no native tool_use). The Tool Executor parses that blob and decides what to
  execute. More control, but you're reimplementing what the API already does,
  and you lose schema enforcement on the tool call arguments.

  Which do you intend? And relatedly — is the reasoning field meant to be the
  model's scratchpad (extended thinking / chain-of-thought that you capture for
  auditability), or a post-hoc explanation the model is asked to write?

  sentence:

  ▎ "Output Filter (rule-based)"

  Then the example: "for lookup_employee this means stripping personal_email,
  personal_phone, home_address, salary, performance_rating, employment_status."

  That example is pure deterministic field-stripping — a fixed list of fields to
   remove based on which tool was called. No LLM needed.

  But "LLM-assisted filtering" implies something more nuanced — e.g., detecting
  when a tool result contains PII that leaked through an unexpected field, or
  when a sequence of results together constitute a prohibited disclosure under
  7.3.

  These are two very different things:

  - A. Purely rule-based — A hardcoded map of tool_name → fields_to_strip. Fast,
   deterministic, testable, zero hallucination risk. (Recommended for initial 
  implementation — covers the explicit prohibitions in the policy exactly.)
  - B. LLM-assisted — A small LLM call that inspects the raw tool output against
   the policy context and strips anything that shouldn't pass. Handles
  unanticipated leakage but adds latency, cost, and non-determinism to every
  tool execution.
  - C. Both, layered — Rule-based first (fast, deterministic), then LLM scan
  only for Confidential/Restricted-touching results. Adds the nuanced check
  where the risk is highest.

  Which do you intend, and does your answer change for different tool types?

⏺ Question 7: How is the policy chunked for retrieval?

  The Policy Retriever does hybrid retrieval — semantic + tag filter +
  cross-reference expansion. But retrieval quality lives or dies on how the
  policy is chunked before it hits the vector store.

  Your policy has a clear structure: 17 sections, each with numbered clauses
  (e.g., 1.1, 1.1.a), tags, cross-references, examples, and exceptions. There
  are several chunking strategies:

  - A. Section-level — Each top-level section (1 through 17) is one chunk.
  Simple, but section 1 alone is ~800 tokens; you'd retrieve the whole
  account-management section when only clause 1.1.b is relevant. Wastes context
  window.
  - B. Clause-level — Each numbered clause (1.1, 1.1.a, 1.1.b) is its own chunk.
   Fine-grained and precise, but cross-references like "escalate per 5.1"
  require the retriever to pull 5.1 separately or risk the Reasoner missing the
  escalation path.
  - C. Section header + clause-level — Each clause chunk includes its parent
  section's header (tags, applies-to, related sections). The cross-reference
  expansion then adds the referenced sections' headers. (Recommended — preserves
   context for each clause while keeping chunks small, and the tags field 
  directly feeds your tag-filter retrieval leg.)
  - D. Semantic paragraphs — Ignore the numbered structure entirely; chunk by
  semantic coherence. Loses the citation anchor (cited_sections in the Reasoner
  Decision needs a stable identifier).

  Given that your Reasoner must cite specific sections (e.g., "3.3" or "4.2.a")
  per policy 6.1, you need chunk identifiers that map to actual section numbers.
   Which chunking strategy fits?

⏺ Question 8: How does cross-reference expansion work, and how deep does it go?

  Each policy chunk includes a "Related sections" field (e.g., section 3.3's
  header lists 5.1, 9.3, 9.4, 14.2, 16.2). Cross-reference expansion means using
   those links to pull in additional chunks. But "expansion" is ambiguous —
  there are several models:

  - A. Shallow, one-hop — After semantic retrieval returns the top-k chunks,
  expand by one level: for each retrieved chunk, also include all chunks listed
  in its "Related sections." Stop there. No recursion. (Recommended — avoids 
  context explosion; one hop covers the critical escalation paths and 
  data-classification constraints that sit adjacent to almost every action 
  clause.)
  - B. Deep, recursive — Follow cross-references transitively until no new
  sections are found. Risks pulling in most of the policy for any request, since
   section 5 (escalation) is cross-referenced by nearly everything.
  - C. Filtered expansion — One-hop, but only expand to cross-references whose
  tags intersect with the tags of the originally retrieved chunks. E.g., if you
  retrieved section 3.3 (tagged file_access, restricted_drives, escalation),
  only expand to cross-referenced sections that share at least one of those
  tags.

  Option B is clearly dangerous given the policy's dense cross-referencing. The
  real question is A vs C: do you want the tag filter to gate expansion, or
  should expansion always be one-hop-flat?

⏺ Question 9: What vector store backs the semantic retrieval leg?

  The policy is small — 17 sections, roughly 600 lines, likely under 200 chunks
  when split at clause level. This changes the infrastructure calculus
  significantly.

  - A. Local in-process (ChromaDB or FAISS) — No network hop, no external
  dependency, runs embedded in the same process. For 200 chunks this is more
  than fast enough. Easy to reset and re-embed during development. (Recommended 
  for take-home scope — the policy is static and small; a hosted vector DB buys 
  you nothing here.)
  - B. Hosted (Pinecone, Weaviate, Qdrant) — Adds a network dependency and
  account setup for a dataset that fits comfortably in memory. Justified when
  the policy scales to thousands of documents or when retrieval needs to be
  shared across services.
  - C. No vector store — brute-force embedding comparison — At 200 chunks,
  cosine similarity over numpy arrays is ~1ms. You could skip the vector DB
  entirely and just load all chunks into memory at startup. Simpler still, but
  less swappable.

  Given your README explicitly says the Policy Retriever "should be swappable,"
  Option A with a thin abstraction layer over ChromaDB (or FAISS) is the natural
   fit — you get a real retriever interface without the hosted dependency. Does
  that align with your intent, or do you have a preference between the two local
   options?

⏺ Question 10: How do you evaluate whether the agent is correct?

  Your README covers the pipeline architecture and cost/latency logging in
  detail, but says nothing about evaluation. For a policy agent where the cost
  of a wrong allow (granting restricted access) is qualitatively different from
  the cost of a wrong deny (blocking a legitimate reset), you need an explicit
  correctness signal.

⏺ Question 12: Is there a session, or is each request stateless?

  The policy has two conflicting pressures here. On one hand, several rules are
  explicitly per-request: section 15 says "check verification state at request
  time, not at session start" and "compliance state must be checked per request,
   not per session." On the other hand, some rules are inherently cumulative
  across a conversation:

  - 5.3.c: "Repeated ambiguity from the same requester within a single session
  is itself a 5.3 trigger"
  - 1.1.b: "at most three password resets within any rolling 30-day window" —
  requires history
  - 7.3: The agent must "consider the cumulative pattern of a session, not only
  the request currently in front of it"

  These can't be enforced in a stateless system. So:

  - A. Fully stateless — Each request is independent. Simpler, but 5.3.c, 7.3,
  and the rate-limit in 1.1.b become unenforceable. (Not recommended — these are
   the exact adversarial-detection clauses the policy is built around.)
  - B. Session state in memory — A session object accumulates request history
  for the duration of a conversation. Enforces 5.3.c and 7.3. The rolling 30-day
   window (1.1.b) still needs a persistent store.
  - C. Session state in memory + persistent store for rate limits — Session
  history in memory for intra-conversation signals; a lightweight persistent
  store (SQLite or a JSON file) for cross-session rate-limit tracking like
  1.1.b. (Recommended — matches the policy's actual requirements precisely.)

  Which model do you want?

⏺ Question 13: Where does cost/latency logging live in the pipeline?

  Your README has unusually detailed logging requirements — per-call latency,
  input/output/cached tokens, tool call costs and latencies individually,
  retries. This is good instrumentation. The question is where it lives
  structurally.

  - A. Wrapper/decorator on every LLM call — A single instrumented_llm_call()
  function wraps every Anthropic API call in the codebase. It captures start/end
   time, parses the response for token counts, computes cost from a prices
  config file, and appends to a structured log. The Policy Retriever and
  Reasoner both go through this wrapper — you instrument once, get coverage
  everywhere. (Recommended — one implementation, zero chance of forgetting to 
  add logging to a new LLM call.)

  time.
  - C. A separate observability component — A dedicated ObservabilityLayer that
  each component reports into after the call. More structured than B, but adds a
   dependency that all components must know about.

  Option A also has a clean answer to where prices live: a model_prices.json or
  prices.py config file that the wrapper reads at import time, keyed by model
  ID. This makes it trivial to update when Anthropic changes pricing.

  Do you want the wrapper approach, and should prices live in a JSON config or a
   Python constants file?

⏺ Question 14: What model(s) do you want, and is the same model used for all LLM

   model — Claude Sonnet 4.6 or Opus 4.7.

  LLM-as-judge setups.)
